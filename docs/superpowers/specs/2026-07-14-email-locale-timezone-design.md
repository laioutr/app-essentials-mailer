# Runtime Email Language Metadata and Configurable Timezone

**Date:** 2026-07-14

## Goal

Make the generated email document metadata match the language of the rendered copy, and allow each deployment to select the timezone used to display submission timestamps instead of requiring UTC.

## Scope

This change applies to the shared form-email renderer and the withdrawal email flow. It does not add new translations or RTL translations. German and English remain the only supported content languages.

## Configuration

Add an optional root property to `MailerConfig`:

```ts
timeZone?: string
```

The value is an IANA timezone identifier such as `Europe/Berlin`.

- A valid configured value is used for date formatting, the visible timezone marker, and the copyright year.
- An omitted value resolves to `UTC` for backward compatibility.
- An invalid value also resolves to `UTC`, as requested, rather than failing email rendering.
- Configuration remains private-only in Nuxt runtime config.
- The module continues its existing no-validation-at-boot design; resolution occurs when the email is rendered.

The README and playground configuration will demonstrate `Europe/Berlin` and document the fallback behavior.

## Locale and Timezone Resolution

Introduce a small shared resolver so content selection, HTML metadata, and date formatting cannot develop conflicting fallback behavior.

For a requested BCP-47 locale, it returns:

- `contentLanguage`: `de` when the language subtag is German; otherwise `en`.
- `direction`: `ltr` for both currently supported content languages.
- `formatLocale`: the complete requested BCP-47 locale, preserving regional date-format conventions.
- `timeZone`: the valid configured IANA timezone, or `UTC` when it is absent or invalid.

Withdrawal-domain strings and renderer-owned chrome use `contentLanguage`. Unsupported content languages therefore use English copy and English document metadata rather than putting an unsupported requested language on English content.

The resolver's content-language result should be reusable by `getWithdrawalStrings` and `renderFormEmail`; timezone resolution is consumed by the renderer.

## Rendering Data Flow

The orchestr action already supplies `clientEnv.locale`. The updated flow is:

1. `handleWithdrawal` resolves withdrawal copy from the request locale.
2. It passes the request locale and `config.timeZone` into each render call.
3. `renderFormEmail` resolves the supported content language, text direction, and effective timezone.
4. It formats `submittedAt` with the complete requested locale and effective timezone.
5. It passes `htmlLang`, `textDirection`, `submittedAt`, `timeZone`, and the timezone-aware copyright `year` into Handlebars.
6. The same values are used for the trader notice and consumer acknowledgement.

`RenderFormEmailOptions.timeZone` and the injected withdrawal `RenderEmail` contract remain optional so direct `/server` API callers preserve the current UTC behavior unless they opt in.

## Template Metadata

The Maizzle shell must retain runtime Handlebars tokens for language metadata. Both document-level locations generated by Maizzle are covered:

```html
<html lang="{{htmlLang}}" dir="{{textDirection}}">
<body xml:lang="{{htmlLang}}" dir="{{textDirection}}">
```

At runtime:

- German content renders `lang="de" dir="ltr"`.
- English content renders `lang="en" dir="ltr"`.
- Unsupported requested languages render English copy and `lang="en" dir="ltr"`.

This corrects the current shell's static English metadata. RTL derivation is intentionally not introduced before an RTL content language exists; when one is added, its supported-language entry can supply `rtl`.

## Timestamp and Year

The timestamp continues using `Intl.DateTimeFormat` with `dateStyle: 'long'` and `timeStyle: 'medium'`, but its `timeZone` option uses the effective timezone.

The footer displays the exact effective IANA identifier:

```text
14. Juli 2026 um 15:30:00 (Europe/Berlin)
```

UTC fallback remains explicit as `(UTC)`.

The copyright year must be derived in the same effective timezone, not with `getUTCFullYear()`. This prevents a timestamp near New Year from displaying one local calendar year while the copyright line displays another. A timezone-aware `Intl.DateTimeFormat` configured for the numeric year can derive it consistently.

## Failure Behavior

Timezone validation is performed through `Intl.DateTimeFormat`, avoiding a separate timezone database or allowlist. Only an invalid configured timezone is converted to `UTC`; unrelated formatting or rendering failures must still propagate.

An invalid locale is outside the new timezone fallback contract. Existing `Intl` locale behavior remains unchanged rather than broadly swallowing errors.

## Testing

### Compiled shell

Verify that Maizzle preserves the `htmlLang` and `textDirection` tokens and that they occur in both the `<html>` and `<body>` language/direction attributes.

### Renderer

Cover:

- German metadata: `lang="de" dir="ltr"`.
- English metadata: `lang="en" dir="ltr"`.
- Unsupported locale: English copy fallback and English metadata.
- A valid `Europe/Berlin` timezone affects the rendered time and shows `(Europe/Berlin)`.
- An omitted timezone uses and shows UTC.
- An invalid timezone falls back to and shows UTC.
- The copyright year follows the effective timezone at a New Year boundary.
- Existing escaping, loops, optional branding, and plaintext behavior remain intact.

Tests should assert deterministic output using fixed dates and locales.

### Withdrawal flow

Verify that configured `timeZone` reaches render calls for both the store notice and consumer acknowledgement. Existing delivery and retry behavior is unchanged.

## Documentation

Update the README configuration example and table with optional `timeZone`. State that it accepts an IANA identifier, affects all displayed timestamps and their calendar year, and falls back to UTC when omitted or invalid.
